# Руководство разработчика: новые модули и общий стиль

Этот проект — набор независимых HTML/CSS/JavaScript-модулей без обязательной сборки. Новые страницы должны выглядеть частью одного продукта, а не отдельными сайтами.

## Главное правило

**Сначала используй общий дизайн-системный слой, не создавай собственную тему.** Перед началом работы посмотри на актуальные модули и CSS в `assets/grain/`. Не копируй старые цвета, шрифты и кнопки из случайного курса.

Основные файлы дизайн-системы:

- `assets/grain/grain.css` — базовые токены и стили Grain.
- `assets/grain/zinc-sky.css` — дополнительные токены и компоненты Zinc/Sky.
- `assets/grain/legacy-course-theme.css` — совместимость со старыми модулями и мост токенов для учебных инструментов.
- `tools/check-new-modules.js` — автоматические проверки некоторых новых модулей и подключения общего стиля.

## Как выбрать тип страницы

### 1. Новый урок или учебный курс

Создай каталог модуля, например `new-topic/index.html`. В начале документа подключи общие таблицы стилей в правильном порядке:

```html
<link rel="stylesheet" href="../assets/grain/grain.css">
<link rel="stylesheet" href="../assets/grain/zinc-sky.css">
<link rel="stylesheet" href="../assets/grain/legacy-course-theme.css">
```

На корневом элементе HTML укажи тему:

```html
<html lang="ru" data-theme="light" data-course-theme="grain">
```

Если у страницы уже есть большой старый встроенный блок `<style>`, подключай `legacy-course-theme.css` **после** него. Для нового модуля предпочтительнее не заводить вторую собственную тему, а использовать общий слой и небольшие локальные стили только для уникальной компоновки.

### 2. Практический инструмент с собственной компоновкой

Для планировщиков, тренажёров и других интерфейсов, где нужна специализированная сетка, оставляй уникальную компоновку, но используй общие токены. Подключи те же три CSS-файла и задай:

```html
<html lang="ru" data-theme="light" data-course-theme="tool">
```

Для вложенных страниц скорректируй относительные пути. Например, из `excel/plan/index.html` путь к CSS начинается с `../../assets/`, а из `plan/index.html` — с `../assets/`.

### 3. Игровой или визуально особенный раздел

Уникальные игровые поля, редакторы диаграмм и визуализации могут иметь собственные стили для содержимого. При этом навигация, заголовки, типографика, кнопки, формы, карточки, состояния фокуса и сообщения должны по возможности следовать общему стилю. Не меняй глобальные токены ради одного игрового элемента: ограничивай стили контейнером модуля.

## Дизайн-правила

- **Цвета:** используй CSS-переменные из Grain/Zinc/Sky. Не добавляй новую палитру с несогласованными зелёными, фиолетовыми или синими оттенками.
- **Типографика:** используй общие переменные шрифтов, размеров и межстрочных интервалов; не подключай случайные шрифты отдельно.
- **Поверхности:** карточки, панели, примеры и квизы должны иметь согласованные фон, границу, радиус и тень.
- **Кнопки и ссылки:** различай основное, вторичное и опасное действие; добавляй заметные состояния hover, focus и disabled.
- **Формы:** у полей должны быть подписи, видимый фокус, понятные ошибки и корректные состояния disabled.
- **Состояния:** прогресс, завершение урока, правильный/неправильный ответ и предупреждения должны быть визуально различимы и доступны не только по цвету.
- **Адаптивность:** проверь узкий экран, отсутствие горизонтальной прокрутки и удобное нажатие на мобильном устройстве.
- **Тёмная тема:** не зашивай белый текст или светлый фон напрямую, если компонент должен поддерживать тему. Проверяй контраст в обеих темах.
- **Доступность:** семантические элементы HTML, корректные `label`, клавиатурная навигация и видимый `:focus-visible`.
- **Область действия CSS:** избегай глобальных правил вроде `button { ... }` или `body * { ... }` для уникального компонента. Ограничивай их корнем своего модуля.

Не переопределяй переменные общего дизайна внутри модуля без веской причины. Если не хватает токена или компонента, сначала проверь, нет ли уже подходящего в общей системе; затем расширяй общий слой, если решение пригодится другим модулям.

## Каркас нового модуля

Минимальный шаблон:

```html
<!doctype html>
<html lang="ru" data-theme="light" data-course-theme="grain">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Название курса — Analyst Prep Kit</title>
  <link rel="stylesheet" href="../assets/grain/grain.css">
  <link rel="stylesheet" href="../assets/grain/zinc-sky.css">
  <link rel="stylesheet" href="../assets/grain/legacy-course-theme.css">
  <style>
    /* Только уникальная компоновка модуля.
       Общие цвета, шрифты и компоненты бери из дизайн-системы. */
    .module-page {
      width: min(100% - 2rem, 72rem);
      margin-inline: auto;
    }
  </style>
</head>
<body>
  <main class="module-page">
    <header class="hero">
      <p class="eyebrow">АНАЛИТИКА ДАННЫХ</p>
      <h1>Название модуля</h1>
      <p class="lead">Краткое описание результата обучения.</p>
    </header>

    <section class="card" aria-labelledby="lesson-title">
      <h2 id="lesson-title">Первый урок</h2>
      <p>Материал урока.</p>
      <button type="button">Проверить ответ</button>
    </section>
  </main>
  <script src="../assets/progress-state.js"></script>
  <script src="./module.js"></script>
</body>
</html>
```

Это каркас структуры, а не обязательная библиотека компонентов: перед использованием конкретных классов проверь существующие страницы и CSS. Не подключай скрипт прогресса, если он не нужен, и соблюдай реальные пути относительно своего каталога.

## Интеграция модуля

Перед завершением проверь, нужны ли изменения в следующих местах:

1. Главная страница и каталог курсов — ссылка на новый модуль.
2. Поиск и карта/маршрут обучения — добавление модуля, если эти механизмы охватывают его тип.
3. Общий прогресс — используй существующий механизм проекта, не создавай параллельное хранилище.
4. DataCraft и награды — если модуль должен открывать уроки на карте или начислять монеты, соблюдай существующие правила награждения и защиту от повторной выдачи.
5. Русский/английский переключатель — новые видимые тексты должны быть совместимы с существующим механизмом локализации.
6. Документация — обнови основной `README.md`, если добавлен новый пользовательский раздел.

Не добавляй отдельные ключи localStorage, глобальные обработчики или вторую систему прогресса, пока не проверил существующие общие механизмы.

## Проверка перед коммитом

- [ ] CSS подключён в правильном порядке и по верным относительным путям.
- [ ] Для курса стоит `data-course-theme="grain"`, для специализированного инструмента — `data-course-theme="tool"`.
- [ ] Страница визуально согласована с существующими модулями: фон, шрифт, карточки, кнопки, формы, состояния и навигация.
- [ ] Светлая тема выглядит корректно; тёмная тема проверена, если она поддерживается.
- [ ] Проверены узкий экран, клавиатурный фокус и читаемость.
- [ ] Уроки, квизы, переходы, прогресс и сохранение работают после визуальных изменений.
- [ ] Ссылки, изображения и скрипты не возвращают 404.
- [ ] Модуль добавлен в нужные каталоги/навигацию и документацию.
- [ ] Запущены доступные проверки проекта, включая `node tools/check-new-modules.js`, если файл присутствует.
- [ ] Не добавлены новые конфликтующие CSS-переменные и повторные глобальные стили.

## Наглядные объяснения в уроках

Учебное объяснение должно помогать ученику увидеть связи между понятиями, а не только читать определения. Для типовых страниц курсов уже есть общий компонент `assets/lesson-visuals.js` и адаптивные стили `assets/lesson-visuals.css`.

### Подключение к новому уроку

Для страницы курса, расположенной на один каталог ниже корня репозитория, подключи CSS после остальных стилей и скрипт перед закрывающим `</body>`:

```html
<link rel="stylesheet" href="../assets/lesson-visuals.css">
<script src="../assets/lesson-visuals.js" defer></script>
```

Компонент определяет текущий курс и заголовок урока, добавляет визуальную опору к каждому статическому уроку или к открытому динамическому уроку. Для нового специфического понятия добавь правило в массив `RULES` файла `assets/lesson-visuals.js`. Сопоставление сначала проверяет заголовок урока, чтобы случайное упоминание термина в тексте не подменяло нужную схему.

### Как выбирать вид схемы

- **Пошаговая схема** — для процессов, порядка действий и логики запроса.
- **Таблица-пример** — для строк, столбцов, типов данных и результата расчёта.
- **Сравнение двух вариантов** — для похожих понятий, типичных ошибок и решений «до/после».
- **Формула с подписями** — когда важно показать, из каких частей получается показатель.
- **BPMN-подобный поток** — для бизнес-процесса с действием и условием. UML используй только там, где он помогает объяснить структуру или взаимодействие объектов; не добавляй диаграмму ради диаграммы.

Каждая схема должна иметь понятный заголовок, короткое объяснение простыми словами, подписи к элементам и практическую мысль, которую стоит запомнить. Она дополняет объяснение и пример, но не раскрывает ответ на проверочное задание. Проверяй мобильную ширину, контраст в светлой и тёмной темах и доступность текста без цвета. Тексты общего компонента помечены `data-no-translate`, потому что они уже написаны по-русски.

## Работа с существующей страницей

Если страница уже имеет собственные стили, не переписывай её логику ради темы. Подключи совместимый слой после старого CSS, замени локальные цвета и компоненты на общие токены постепенно, затем проверь интерактивность. Уникальные стили допустимы для содержимого, но не должны визуально превращать модуль в отдельный продукт.
