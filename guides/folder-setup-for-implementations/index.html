Setting Up Files and Folders for a SaaS Implementation

Config, data and document migration, testing, training and handover, in one structure you can copy for every client

By Michael Nocito, Implementation Analyst · Published October 23, 2026

By the end of this page you can set up one folder template that fits any software implementation, name files so a colleague can find them without asking you, keep every migration load traceable and reversible, and hand a client a clean package at the end. It is about twenty minutes to read and about fifteen to apply, and it works the same whether you run one project or several at once.

Here is what to do today. Build the empty template once (section 2), then copy it for your next project instead of starting from a blank folder. That one habit does most of the work on this page, because every project then looks the same and you stop making layout decisions mid-project.

The short version: number the folders in project order, never edit the client’s original files, log every decision and every load, and keep the proof (counts, sign-offs, test results) in the folder rather than in somebody’s inbox.

1. One client, one folder, one template

An implementation produces a lot of paper: requirements, a configuration workbook, mapping specs, extracts, load files, test scripts, training decks, sign-offs. Put all of it under one folder per client, built from the same template every time.

The template matters more than the structure inside it. When every project has the same folders in the same order, you can open any client and know where the mapping spec is, a teammate can cover for you, and the questions you ask yourself at go-live (where is the last load file? where is the sign-off?) have the same answer on every project.

2. The structure

Numbered by project phase, so the folder listing is also the project plan.

ACME_implementation/
├── 00_admin/          contract, SOW, contacts, project plan
├── 01_discovery/      requirements, workflow notes, kickoff
├── 02_configuration/  config workbook, decisions, screenshots
├── 03_data_migration/
│   ├── 01_source/         client extracts, untouched
│   ├── 02_mapping/        field mapping specs
│   ├── 03_transformed/    cleaned files, ready to load
│   ├── 04_loads/          one folder per load, dated
│   └── 05_reconciliation/ source vs target, signed off
├── 04_documents/      document migration inventory and results
├── 05_testing/        test scripts, results, defects, UAT sign-off
├── 06_training/
│   ├── admin/
│   └── end_user/
├── 07_go_live/        cutover plan, checklist, rollback plan
├── 08_handover/       as-built record, support contacts
└── 99_archive/        superseded files, nothing deleted

The numbers do two jobs. They sort the folders in lifecycle order on every computer, and they give you a shorthand: “it’s in 03” is enough for anyone who has seen the template once. Leave gaps (00, 99) so you can add a phase without renaming everything.

3. Naming that survives eight projects at once

One pattern for every file, with the client first so a search across all your projects sorts by client.

CLIENT_topic_description_vNN_YYYY-MM-DD.ext

ACME_mapping_contracts_v03_2026-10-23.xlsx
ACME_load02_contracts_2026-10-27.csv
ACME_training_admin_deck_v02_2026-11-04.pptx
PartRule
Client codeA short fixed code, the same on every file for that client.
TopicLowercase. Matches the phase: mapping, load, test, training.
Versionv01, v02. Two digits so they sort. Increase on every change that someone else may have seen.
DateYYYY-MM-DD, so files sort by time.
Never“final”, “new”, “latest”, “copy”, or a person’s initials. final_v2_REAL is how teams lose a week.

No spaces in file names, because they break scripts, links and some import tools.

4. Source files are read-only

Whatever the client sends you, whether a database extract, a spreadsheet or a folder of scanned documents, goes into 01_source exactly as received and is never opened and re-saved. Work on a copy.

The reason is evidence. When a record is wrong in the new system, the first question is whether it was wrong in the source or broken by you. If the original is untouched, you can answer in a minute. If you “just tidied” it, you cannot, and you have no standing to say whose fault it is.

Add the date you received it to the file name, and save the email or message it came with. A source file without a date is a source file you cannot place.

5. Configuration

Configuration is the part most likely to live only in someone’s head, and it is the part the client will ask about in a year.

Keep three things in 02_configuration:

FileWhat it holds
Configuration workbookEvery setting you chose, one row each: area, setting, value, who decided, date. This is the source of truth, and the system is built from it, not the other way round.
Decision logAnything where the client chose between options: what the options were, what they picked, who approved it, when.
ScreenshotsThe final state of each configured area, named by area and date. One screenshot is worth a paragraph of description.

Record a setting at the moment you make it, not at the end. A configuration workbook written from memory after go-live is a guess, and it will be wrong in exactly the places that matter.

If you configure a test environment first and then repeat the work in production, the workbook is also your checklist for the second pass. Mark each row as done in each environment, so nothing is configured in one and forgotten in the other.

6. Data migration

Data migration is where an implementation succeeds or fails, and it is the part with the most files. The folders in section 2 are a pipeline: each one is a stage, and files only move forward, never backward.

01_source  →  02_mapping  →  03_transformed  →  04_loads  →  05_reconciliation
 as received   how fields     cleaned, ready    what was      proof it matches
               map across     to load           loaded        the source

Mapping. One mapping spec per object (contracts, users, locations): source field, target field, transformation rule, default for blanks, and an owner for every open question. The mapping spec is the contract between you and the client about what moves and how. Version it, and note which version each load used.

Loads. Every load gets its own dated folder, even a rerun of a failed one.

04_loads/
└── load02_contracts_2026-10-27/
    ├── ACME_load02_contracts_2026-10-27.csv   exactly what was loaded
    ├── load_notes.txt                          mapping version, row count, who ran it
    └── errors_2026-10-27.csv                   rows the system rejected

Keep the file you actually loaded, not the file you meant to load. If something needs to be reversed or explained later, that file is the only thing that tells you what went in.

Reconciliation. After every load, compare the target against the source and save the result in 05_reconciliation. At minimum: record counts in and out, and totals on any numeric field that matters (contract value, quantity, balance). A reconciliation that shows source 1,000, loaded 1,000 and rejected 0 is evidence. “It looked fine” is not.

Do not sign off a load until the numbers match or every difference is explained in writing. A short note such as “12 rejected: duplicate IDs, listed in errors file” is enough, and it is the thing that protects you when someone asks about it later.

Any load you may need to undo should be loadable in a way you can reverse, for example by tagging loaded records with a batch or load ID. Decide this before the first load, because it cannot be added afterwards.

7. Document migration

Documents are migrated by the thousand, so the folder is not enough on its own. You need a manifest: one spreadsheet with one row per document.

ColumnPurpose
doc_idA unique ID you assign. Never reuse one.
original_pathWhere the file was. The only way back to the source.
original_nameThe name it arrived with.
new_nameThe name it has after migration.
doc_typeCategory in the new system.
linked_recordThe record it attaches to, such as a contract ID.
statusPending, uploaded, failed, excluded.
notesWhy it failed or was excluded.

The manifest is also your reconciliation. Files in the source folder, rows in the manifest, documents in the new system: three numbers that must agree, or the gap must be explained. Check a sample by opening ten documents in the new system and comparing them to the originals, because a count cannot tell you that a file uploaded blank.

Keep the original names in the manifest even when you rename files. Clients search by the old name for years.

8. Testing and UAT

Four things in 05_testing: the test scripts, the results, the defect list, and the sign-off.

A test script is a numbered list: what to do, what should happen. Write them from the client’s real workflows, not from the system’s menu. Record the result next to each step, with the date and who ran it. A defect list needs one row per problem: what happened, severity, who owns it, status, and the date it was closed.

The sign-off is the part people leave out. When the client accepts UAT, save that acceptance, whether it is a signed form or an email exported to PDF, in the same folder. It is the record that go-live was agreed, and it is much easier to save at the time than to find later.

9. Training: admin and end user

Keep the two audiences in separate folders, because they need different material and different timing.

Admin trainingEnd-user training
GoalRun and maintain the systemDo their job in it
ContentConfiguration, user setup, reports, troubleshootingThe few tasks they do daily
MaterialsAgenda, deck, exercises, admin guideQuick reference guide, short walkthrough, practice tasks
TimingBefore UAT, so admins can help testClose to go-live, so it is fresh

For each session, keep in the folder: the agenda, the exact deck or guide used (with version and date), the practice exercises, an attendance list, and any recording. Write the materials against the system as configured, with the client’s own field names and screens, not the generic product. Training on a screen that does not match the live system is the fastest way to generate support calls.

An end-user quick reference guide should fit on one page: the five things they do most, in the order they do them. Anything longer will not be opened.

10. Decisions, changes and sign-offs

Most implementation disputes are about what was agreed. Three small files prevent most of them, all in 00_admin:

FileOne row per
Decision logDecision: what, who decided, date, link to the evidence.
Change logChange to scope: what, why, impact, who approved.
Risks and issuesRisk or issue: description, owner, next step, status.

Save meeting notes in the same folder, dated, with actions and owners at the top. If a decision was made in a call or an email, write one line in the log the same day. A decision that exists only in an inbox is a decision you will have to prove later.

11. Go-live and handover

07_go_live holds a cutover plan (what happens, in what order, who does it, how long it should take), a go-live checklist, and a rollback plan: what you do if it goes wrong and who decides. Write the rollback plan before you need it.

08_handover is what the client keeps. At the close of the project, put together:

  • An as-built record: the final configuration workbook and key screenshots.
  • Migration summary: what was moved, counts, known exceptions.
  • Training materials, final versions.
  • Open items and who owns each.
  • Support contacts and how to raise a request.

Then close the project properly: move superseded files to 99_archive, and follow whatever the contract says about retaining or deleting client data.

The question about the 40 contracts is answered by opening the reconciliation file and the errors file from the load. Nothing about the work changed. What changed is that the evidence exists and you can find it in a minute.

Edge cases worth knowing

Six that come up.

Client data is sensitive. Extracts often contain personal or regulated information. Keep it only in the locations the contract allows, not on a personal drive or a USB stick, and do not email it. Check the retention terms and delete or return the data when the project closes.

No credentials in files. Never store passwords, API keys or logins in a spreadsheet or document in the project folder. Use a password manager and put only a pointer in the folder.

Email is not a filing system. A requirement agreed by email exists only for the person who has the email. Save the message into 00_admin or log it the same day.

Sandbox and production look alike. Put the environment in the name of anything that touches the system (_sandbox, _prod) so a load file for one cannot be mistaken for the other.

Shared folders create conflicts. Two people editing the same workbook in a synced folder produce “conflicted copy” files. Agree who owns each file, and use the version number to hand it over.

Scope creep arrives as small files. A new spreadsheet “just to try something” is often a new requirement. If it is new scope, it goes in the change log.

Why this works

The folder principles are the same ones people who study reproducible work recommend: keep raw inputs separate from anything derived, never change the raw copy, give each project one folder with a consistent layout, and name things so someone else can tell what they are (Wilson et al., 2017, PLOS Computational Biology, 13(6), e1005510). A migration is a derived-data pipeline, so the same discipline applies.

The checklists, logs and sign-offs follow a related idea: in complex work where a missed step is costly, writing the steps down and ticking them off catches errors that experience alone does not (Gawande, 2009, The Checklist Manifesto, Metropolitan Books). The cutover plan, the load notes and the go-live checklist are all that idea applied to implementation.

The cheat sheet below is built to be covered and recalled rather than reread, because reviews of study techniques put practice testing and spacing near the top of what works and rereading and highlighting near the bottom, despite rereading feeling much more productive (Dunlosky, Rawson, Marsh, Nathan, & Willingham, 2013, Psychological Science in the Public Interest, 14(1), 4–58).

Using this on your own project

Do this once for the template, then once per client. About fifteen minutes the first time.

  1. Build the template. Create the folders from section 2 and save the empty tree as _TEMPLATE_implementation.
  2. Add starter files. Blank decision log, change log, configuration workbook, mapping spec, manifest and reconciliation sheet, saved in the right folders.
  3. For each client, copy the template and rename it with the client code.
  4. Save the source as received into 01_source with the date, and never edit it.
  5. Log as you go. Every decision, every setting, every load, the same day.
  6. Reconcile every load and save the proof before moving on.
  7. Save the sign-offs for UAT and go-live where you can find them.
  8. At close, hand over and archive. Fill 08_handover, move old files to 99_archive, and apply the data retention terms.

If you have paper nearby, one optional sketch is worth five minutes. Draw the project as a line from kickoff to go-live, and under each phase write the one file that proves it happened. Any phase where you cannot name that file is a gap in your records.

The one habit to keep. Save the proof when the thing happens, not when someone asks for it. A reconciliation, a sign-off or a decision recorded on the day takes two minutes; the same thing reconstructed three months later takes an afternoon, and is worth less.
