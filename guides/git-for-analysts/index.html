Git и GitHub для аналитиков

Ежедневный цикл сохранения и публикации, без жаргона · Часть Analyst Prep Kit

By Майкл Носито, аналитик данных · Обновлено 30 июля 2026 г.

Git выглядит как стена страшных команд. Как аналитику вам нужно только небольшое, повторяемое ядро: сохраните свою работу с заметкой и отправьте ее на GitHub, чтобы ее можно было создать резервную копию и поделиться ею. Это 90% того, что вы когда-либо сделаете. Это руководство учит этому основному. Затем показано, как запустить проект и опубликовать его в виде действующей веб-страницы. Наконец, в нем перечислено несколько ошибок, которые сбивают всех с толку в первый раз.

Git против GitHub, в одну строку. Git это инструмент на вашем компьютере, который отслеживает изменения в ваших файлах. GitHub — это веб-сайт, который хранит копию в Интернете, поэтому ее можно резервировать, использовать для совместного использования и (с помощью GitHub Pages) можно разместить действующий сайт. Вы используете Git локально; вы отправляете на Гитхаб.
Что вы узнаете
  1. Установите Git и войдите в систему один раз.
  2. Ежедневный цикл: статус, добавление, фиксация, отправка
  3. Начните новый проект и разместите его на Гитхаб.
  4. Опубликуйте его как действующий сайт с помощью Страницы GitHub.
  5. Чего НЕ следует совершать (и как)
  6. Исправьте пять ошибок, с которыми каждый сталкивается однажды

Шаг 1. Установите Git и укажите свою личность (один раз).

  1. Установите Git из git-scm.com/downloads (все значения по умолчанию в порядке).
  2. По желанию установите Интерфейс командной строки GitHub from cli.github.com. Это значительно упрощает создание репозиториев и вход в систему.
  3. Откройте терминал (Гит Баш в Окна, Терминал на Мак) и сообщите Git, кто вы. Это имя и адрес электронной почты отмечаются при каждом сохранении:
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Если вы установили интерфейс командной строки GitHub, войдите в GitHub один раз с помощью gh auth login и следуйте подсказкам. Это то, что позволяет вам нажимать, не вставляя пароль каждый раз.

Шаг 2. Ежедневный цикл (это 90% Git)

Почти всю работу выполняют три команды, и они всегда выполняются в одном и том же порядке. Прочитав их, закройте блок и произнесите три обратно по порядку, потому что вы будете печатать эту последовательность чаще, чем все остальное в этом руководстве вместе взятое.

Каждый раз, когда вы заканчиваете часть работы, вы делаете одно и то же трехтактное движение: этап, сохранение, отправка. В терминале, открытом внутри папки вашего проекта:

git status                 # see what changed (read this first, always)
git add .                  # stage every changed file for the next save
git commit -m "Add churn analysis notebook"   # save, with a short note
git push                   # send it up to GitHub

Вот и весь суточный ритм. status показывает вам, что будет сохранено, add выбирает файлы, commit сохраняет снимок с сообщением и push загружает его. Делайте это часто, используя четкие сообщения. Думайте о каждом коммите как о помеченной точке сохранения, к которой вы можете вернуться.

Напишите сообщения о коммитах, которые сможет прочитать незнакомец. «Исправление» ничего не скажет вам за три недели. «Исправить неправильный анализ даты в отчете о продажах» точно расскажет вам, что это была за точка сохранения. Настоящее время, одна строка, конкретное.

Шаг 3. Запустите новый проект и разместите его на Гитхаб.

У вас есть папка с вашей работой, и вы хотите, чтобы она была на Гитхаб. Из этой папки:

git init -b main           # start tracking this folder, on a branch called main
git add .                  # stage everything
git commit -m "First commit"   # your first save point

Теперь создайте для него онлайн-дом. Самый простой способ — с помощью Интерфейс командной строки GitHub — сделать это в одну строку и одновременно нажать:

gh repo create my-project --public --source=. --remote=origin --push

Нет CLI? Создайте пустой репозиторий на github.com/новый (не добавляйте README, оставьте его пустым). Затем скопируйте две команды, которые GitHub показывает вам в разделе «Отправить существующий репозиторий». Они выглядят так:

git remote add origin https://github.com/yourname/my-project.git
git push -u origin main

Шаг 4. Опубликуйте его как действующий веб-сайт (страницы GitHub).

Если в вашем проекте есть index.html, GitHub может бесплатно разместить его как настоящую общедоступную веб-страницу. На странице репо: Настройки → Страницы → Источник: Развернуть из ветки → Ветка: основная/(корневая) → Сохранить.

Подождите одну-две минуты до первой сборки, затем посетите:

https://yourname.github.io/my-project/
Подождите минуту и ​​обновите. GitHub Pages не обновляется в момент нажатия. Первая сборка занимает минуту или две, а последующие изменения могут храниться в кеше вашего браузера. Если вы не видите изменения, подождите, а затем выполните принудительное обновление (Ctrl+Shift+R). На самом деле он почти никогда не ломается.

Шаг 5. Чего НЕ следует совершать

Прежде чем читать список, подумайте о папке своего проекта. Какой файл из него вам было бы больше всего неловко случайно опубликовать в Интернете? Этот файл является причиной существования этого шага.

Git предназначен для вашего кода и небольших файлов, а не для гигантских наборов данных. GitHub отклоняет файлы размером более 100 МБ, а использование CSV-файла размером 2 ГБ или файла базы данных в любом случае является ошибкой. Вы исключаете файлы, перечисляя их в .gitignore файл в корне вашего проекта:

# .gitignore
*.db            # SQLite databases
*.csv           # large raw data
data/raw/       # a whole folder of source files
node_modules/   # dependencies

Эмпирическое правило: делайте то, что необходимо rebuild проект (код, небольшой пример файла, README), а не сами тяжелые данные. Любой может повторно загрузить или восстановить большие файлы.

Пять ошибок, которые каждый совершает однажды

Все пять из них остановили кого-то на день, и ни один из них не означает, что вы что-то сломали. Прежде чем читать исправление, прочитайте каждое сообщение и попытайтесь сказать, на что жалуется Гит. Сообщения плохо сформулированы, не сложны.

1. «Обновления отклонены... сначала скачайте»

Ваш запрос не был отклонен, поскольку в GitHub есть изменения, которых нет на вашем компьютере (обычно, если вы редактировали файл на веб-сайте или работаете на двух машинах). Сначала потяните, затем нажмите:

git pull --rebase
git push

2. Он запрашивает пароль и отклоняет его.

GitHub прекратил принимать пароли учетных записей через Git в 2021 году. Либо войдите в систему один раз с помощью gh auth login (самый простой) или создайте Токен личного доступа (GitHub → Настройки → Настройки разработчика → Токены личного доступа) и вставьте этот токен туда, где он запрашивает пароль.

3. «предупреждение: LF будет заменен на CRLF»

Безвреден. Просто Git отмечает, что Окна и Мак/Линукс по-разному отмечают окончания строк. С вашими файлами все в порядке. Не обращайте на это внимания.

4. Вы случайно зафиксировали огромный файл

Добавьте это в .gitignore, затем прекратите его отслеживание (при этом он будет удален из Git, но останется на вашем диске):

git rm --cached bigfile.csv
git commit -m "Stop tracking large data file"

5. «фатально: не мерзавец-репозиторий»

Вы запускаете Git в папке, которая никогда не запускалась git init, или вы находитесь на одну папку слишком высоко или слишком низко. Проверьте, где вы находитесь, и убедитесь, что вы находитесь внутри папки проекта.
