Урок 1. Как Power BI воспринимает данные (Таблицы и уровень детализации)
Раздел: Часть 0: Прежде чем строить
Кратко:
Таблицы, строки и определение того, что представляет собой одна запись (уровень детализации / Grain).
Рабочая ситуация:
Ваш руководитель объявляет, что аналитическая команда переходит на Power BI для подготовки всей корпоративной отчетности. Прежде чем перетаскивать поля на холст отчета, необходимо понять, как именно Power BI видит данные. Все сущности — продажи, клиенты, справочники товаров — хранятся в виде таблиц. У каждой таблицы есть уровень детализации (зернистость): что именно означает одна строка. Если уровень детализации определен верно, каждая последующая мера DAX и визуальный элемент будут рассчитываться корректно.
Теория:
Power BI работает с таблицами по аналогии с реляционными базами данных или электронными таблицами. Каждый подключенный источник становится таблицей в модели данных. Таблица состоит из строк (записей) и столбцов (полей). Главное понятие — уровень детализации (Grain): что представляет собой отдельная строка. Одна строка = одна транзакция? Одна строка = один клиент? Ошибки при определении зернистости — главная причина искажения показателей в Power BI и появления двойного учета в вычислениях DAX.
Разбор и примеры:
\* Таблица продаж: одна строка = одна транзакция (покупка)
\* Справочник клиентов: одна строка = один уникальный клиент
\* Справочник товаров: одна строка = один артикул (SKU)
\* Агрегированная таблица за день: одна строка = суточные итоги
Каждая таблица выполняет строго одну задачу. Прежде чем писать меры, четко сформулируйте уровень детализации каждой таблицы.
Основные понятия:
\* Таблица (Table): двухмерная сетка из строк и столбцов, базовая единица модели данных Power BI.
\* Строка / Запись (Row / Record): одно конкретное наблюдение (продажа, клиент, продукт).
\* Столбец / Поле (Column / Field): атрибут сущности (Регион, Выручка, Дата, ID клиента).
\* Уровень детализации (Grain): бизнес-смысл одной строки в таблице.
\* Двойной учет (Double counting): ошибка, возникающая при неверном связывании таблиц с различным уровнем детализации.
Важно запомнить:
Представьте кассовый чек: сам чек — это покупка в целом, но каждая позиция в чеке — это отдельная строка. Позиция чека — это и есть уровень детализации. Звездообразная схема Power BI (Star Schema), состоящая из одной таблицы фактов и нескольких таблиц измерений (справочников), предназначена для сохранения четкой структуры. Таблица фактов продаж должна находиться на уровне отдельной транзакции, а справочники — на уровне уникальных сущностей. Корректная настройка связей предотвратит двойной учет.
Визуализация зернистости:
\* 1 строка = 1 транзакция (Таблица фактов «Продажи»)
\* 1 строка = 1 клиент (Измерение «Клиенты»)
\* 1 строка = 1 SKU (Измерение «Товары»)
Связывайте таблицы измерений с таблицей фактов по первичным и внешним ключам (Primary Key / Foreign Key). Это гарантирует точность вычислений.
Проверка понимания:
Вопрос: В вашей таблице «Продажи» одна строка соответствует отдельной позиции заказа, а не заказу целиком. В чем заключается опасность при построении модели?
\* Вариант 1 (Правильный): В связях — создание связи «один ко многим» по ID заказа приведет к размножению строк и завышению итогов.
\* Вариант 2: В обычных мерах SUM — повторный подсчет строк приведет к ошибкам.
\* Вариант 3: Детализация позиций не подходит для таблицы фактов.
\* Вариант 4: Зернистость не влияет на модель Power BI.

Бизнес-контекст:
Уровень детализации определяет, что именно измеряется. Если итоговая сумма кажется слишком большой, первоочередная проверка — соответствие зернистости таблиц в связях модели.

Урок 2. Типы данных и их значение в Power BI
Раздел: Часть 0: Прежде чем строить
Кратко:
Почему несоответствие типов данных приводит к незаметным ошибкам в агрегациях.
Рабочая ситуация:
Вы определили уровень детализации таблиц. Следующий шаг — проверка типов данных. Число, сохраненное как текст, не будет суммироваться. Столбец даты, распознанный как текст, заблокирует функции аналитики дат (Time Intelligence). Power BI обозначает типы данных значками в представлениях «Таблицы» и «Модель». Своевременное исправление типов данных сэкономит часы отладки.
Теория:
Power BI присваивает тип данных каждому столбцу: целое число (Integer), десятичное число (Decimal Number), текст (Text), дата (Date), дата/время (DateTime), логический тип (True/False). Тип определяет допустимые операции: числа можно суммировать, даты — фильтровать по периодам, текст — объединять. Неверный тип данных приводит к скрытым ошибкам: функция SUM возвращает пустая ячейка (BLANK), графики не отображают данные. Исправляйте типы данных в редакторе Power Query до загрузки в модель.
Типы данных:
\* Целое число (Integer): количества, идентификаторы (ID), счетчики.
\* Десятичное число (Decimal Number): цены, суммы, доли, проценты.
\* Текст (Text): наименования, коды, категории, регионы.
\* Дата (Date): календарные даты (без указания времени).
\* Логический (True/False): бинарные флаги и условия.
Важно запомнить:
В Power Query обращайте внимание на заголовки столбцов. Значки 123, 1.2, ABC, 📅 показывают текущий тип. Не полагайтесь полностью на автоматическое определение типов Power Query при импорте из CSV или Excel.
Влияние типов данных на вычисления:
\* Числовой тип: SUM, AVERAGE, COUNT, MIN, MAX работают корректно.
\* Текстовый тип (для чисел): SUM возвращает BLANK или ошибку без явного предупреждения.
\* Тип Дата: работают функции Time Intelligence (TOTALYTD, SAMEPERIODLASTYEAR).
Проверка понимания:
Вопрос: Столбец «Revenue» (Выручка) импортирован как текст. Вы создаете меру: Общая выручка = SUM(Sales[Revenue]). Что вернет мера?
\* Вариант 1: Правильную сумму.
\* Вариант 2: 0.
\* Вариант 3 (Правильный): Пустое значение (BLANK) без вывода сообщения об ошибке.
\* Вариант 4: Ошибку синтаксиса.

1. Открыть Power Query (Преобразование данных)
2. Выбрать столбец Revenue
3. Изменить тип данных: Текст → Десятичное число
4. Нажать «Закрыть и применить»
Практика:
Вопрос: Столбец «OrderDate» импортирован как текст. Где правильнее всего исправить тип данных?
\* Ответ: В редакторе Power Query изменить тип столбца на «Дата», затем нажать «Закрыть и применить».

Урок 3. Понятие агрегации в Power BI
Раздел: Часть 0: Прежде чем строить
Кратко:
Принцип, лежащий в основе работы карточек KPI, гистограмм и мер DAX.
Рабочая ситуация:
В модели хранятся тысячи строк с детальными транзакциями, а руководству нужна итоговая выручка. Агрегация сворачивает множество строк в один показатель: SUM складывает значения, COUNT подсчитывает количество строк, AVERAGE находит среднее. Любая визуализация Power BI отображает агрегированные данные.
Теория:
Каждый визуальный элемент в Power BI агрегирует строки таблицы в соответствии с контекстом фильтра. Например, гистограмма выручки по регионам рассчитывает SUM(Sales[Revenue]) для каждого региона. Карточка KPI без фильтров показывает сумму по всей таблице.
Примеры мер DAX:// Явная мера суммирования
Общая выручка = SUM(Sales[Revenue])
// Подсчет количества заказов (строк)
Количество заказов = COUNTROWS(Sales)
// Расчет среднего чека
Средний чек = AVERAGE(Sales[Revenue])
Основные термины:
\* Имя меры: название слева от знака =.
\* Агрегирующая функция: SUM, COUNTROWS, AVERAGE, MIN, MAX.
\* Контекст фильтра (Filter Context): текущий набор фильтров, действующих на визуальный элемент (выбранный регион, дата, срез).
Важно запомнить:
При перетаскивании числового поля на холст Power BI создает неявную меру (Implicit Measure). По умолчанию применяется SUM. Если вместо общей суммы по региону отображаются отдельные строки, отключите параметр «Не суммировать» в настройках поля. Хорошая практика — всегда создавать явные меры (Explicit Measures) на языке DAX.
Проверка понимания:
Вопрос: Вы перетащили поле «Выручка» в область «Значения» гистограммы и увидели отдельные столбцы для каждой транзакции вместо итогов по регионам. В чем причина?
\* Ответ: Для поля «Выручка» установлено значение «Не суммировать» (или отсутствует поле категории на оси).
Конструктор процесса агрегации:
1. Выборка всех строк таблицы «Продажи».
2. Фильтрация строк по текущему контексту (например, Region = "West").
3. Вычисление SUM(Sales[Revenue]) по отфильтрованным строкам.
4. Отображение итогового значения на визуальном элементе.
Практика:
Вопрос: Перетаскивание поля «Выручка» создает неявную сумму. Как выглядит явный аналог на DAX?
\* Ответ: Общая выручка = SUM(Sales[Revenue]).

Вы поняли механизм агрегации данных в Power BI под воздействием контекста фильтра.
Урок 4. Цикл разработки в Power BI (Загрузка, Трансформация, Анализ)
Раздел: Часть 0: Прежде чем строить
Кратко:
Трехэтапный рабочий процесс любого проекта в Power BI.
Рабочая ситуация:
Вы усвоили принципы зернистости, типов данных и агрегации. Пора рассмотреть сквозной цикл разработки Power BI: Загрузка (получение данных), Трансформация (очистка в Power Query) и Анализ (моделирование, DAX, визуализация).
Теория:
Процесс создания отчета состоит из трех последовательных фаз:
1. Загрузка (Load): подключение к источникам данных (Excel, SQL, CSV, Web, SharePoint) через меню «Получить данные».
2. Трансформация / Формирование (Transform / Shape): очистка и подготовка данных в Power Query (переименование столбцов, изменение типов, удаление дубликатов и пустых строк).
3. Анализ (Analyze): связывание таблиц в схему «звезда» в представлении «Модель», написание мер на DAX, построение визуализаций на холсте отчета.
Схема цикла:
Загрузка (Get Data) → Трансформация (Power Query) → Анализ (Model / DAX / Report)
Важно запомнить:
Распространенная ошибка — выполнение очистки данных на этапе анализа с помощью вычисляемых столбцов DAX. Очистка, изменение типов и форматирование столбцов должны выполняться в Power Query. Это обеспечивает высокую скорость работы модели данных.
Проверка понимания:
Вопрос: Столбец называется dt\_order, а должен называться Дата заказа. На каком этапе правильнее выполнить переименование?
\* Ответ: В Power Query на этапе трансформации данных.
Конструктор последовательности:
1. Загрузка: Получить данные → Выбор источника
2. Трансформация: Power Query → Исправление типов, очистка, фильтрация
3. Анализ: Настройка связей → Создание мер DAX → Построение визуализаций
Практика:
Вопрос: В CSV-файле внизу присутствуют 40 пустых строк. Какой инструмент должен их удалить?
\* Ответ: Редактор Power Query на этапе трансформации.
Итог урока:
Вы освоили правильную последовательность этапов разработки в Power BI.
Урок 5. Интерфейс Power BI Desktop
Раздел: Глава 1: Интерфейс и работа с данными
Кратко:
Основные области управления Power BI Desktop.
Рабочая ситуация:
Вы изучили методологический фундамент. Теперь откройте Power BI Desktop и ознакомьтесь с интерфейсом. Слева расположены три основных представления, справа — рабочие панели.
Теория:
В Power BI Desktop есть три ключевых представления:
1. Представление «Отчет» (Report View): холст для создания визуализаций и дашбордов.
2. Представление «Таблицы» (Data/Table View): просмотр загруженных таблиц, строк и столбцов.
3. Представление «Модель» (Model View): схема связей между таблицами.
Основные панели справа:
\* Панель «Данные» (Fields/Data): список всех таблиц и столбцов модели.
\* Панель «Визуализации» (Visualizations): выбор типов диаграмм, настройка осей, значений и форматирование.
\* Панель «Фильтры» (Filters): фильтрация на уровне визуального элемента, страницы или всего отчета.
Панели интерфейса:
Название панели
Назначение
Визуализации
Выбор типа диаграммы и перетаскивание полей в области осей/значений
Данные
Список таблиц, столбцов и мер модели
Фильтры
Управление фильтрами (Визуальный элемент / Страница / Все страницы)
Важно запомнить:
Панель «Фильтры» имеет три уровня применения:
\* Фильтр для этого визуального элемента.
\* Фильтр для этой страницы.
\* Фильтр для всех страниц отчета.
Проверка понимания:
Вопрос: Какое представление позволяет просматривать и настраивать связи между таблицами?
\* Ответ: Представление «Модель» (Model View).
Маршрут проверки данных:
1. Представление «Таблицы» — проверка загруженных строк и типов данных.
2. Представление «Модель» — проверка корректности связей между таблицами.
3. Представление «Отчет» — построение визуализаций на холсте.
Практика:
Вопрос: Вам необходимо связать Sales[CustomerID] с Customers[CustomerID]. Где это делается?
\* Ответ: В представлении «Модель» путем перетаскивания связи между ключевыми полями.

Урок 6. Подключение к данным и Power Query
Раздел: Глава 1: Интерфейс и работа с данными
Кратко:
Импорт данных через «Получить данные» и обработка в Power Query.
Рабочая ситуация:
Первый практический шаг любого проекта — импорт данных. Нажмите «Получить данные», укажите источник и откройте Power Query для очистки.
Теория:
Команда Получить данные (Get Data) позволяет подключаться к сотням источников. Редактор Power Query — это ETL-среда Power BI. Все действия, выполняемые в Power Query, записываются в виде цепочки шагов на панели Примененные шаги (Applied Steps).
Основные этапы:Главная → Получить данные → Выбор источника (SQL / Excel / CSV)
↓
Редактор Power Query (Преобразование данных)
↓
Панель «Примененные шаги» (Автоматическая запись преобразований)
↓
Закрыть и применить (Загрузка очищенных данных в модель)
Важно запомнить:
Все действия в Power Query обратимы. Панель «Примененные шаги» хранит историю операций. При нажатии кнопки Обновить (Refresh) Power BI автоматически выполнит всю цепочку шагов к новым данным источника.
Проверка понимания:
Вопрос: Где выполняются очистка и преобразование данных перед их загрузкой в модель?
\* Ответ: В редакторе Power Query.
Конструктор воспроизводимого импорта:
1. Главная → Получить данные → Выбор источника
2. Power Query → Очистка, переименование, настройка типов
3. Нажать «Закрыть и применить»
4. При обновлении данных шаги выполнятся автоматически
Практика:
Вопрос: В исходном CSV-файле некорректные заголовки и числа записаны как текст. Когда их исправить?
\* Ответ: В Power Query до нажатия кнопки «Закрыть и применить».
Итог урока:

Урок 7. Создание первого визуального элемента
Раздел: Глава 1: Интерфейс и работа с данными
Кратко:
Выбор типа диаграммы и настройка областей полей (Field Wells).
Рабочая ситуация:
Данные загружены, очищены и связаны. Теперь переходим к созданию визуализаций: выберите тип диаграммы и перетащите поля в соответствующие области.
Теория:
Создание визуального элемента состоит из выбора типа диаграммы на панели «Визуализации» и заполнения областей полей:
\* Ось / Категории (Axis / Category): поле для группировки по оси X (категория, регион, дата).
\* Значения (Values): числовое поле или мера DAX для вычисления показателей по оси Y.
\* Легенда (Legend): поле для дополнительной детализации и цветового разделения серий.
Алгоритм построения:
1. Выберите тип диаграммы на панели «Визуализации».
2. Перетащите категориальное поле в область «Ось».
3. Перетащите числовое поле или меру в область «Значения».
4. При необходимости добавьте поле в область «Легенда».
Важно запомнить:
Power BI автоматически агрегирует данные в области «Значения». Для изменения типа агрегации нажмите правую кнопку мыши на поле в области «Значения» и выберите нужную функцию (Сумма, Среднее, Количество, Минимум, Максимум).
Проверка понимания:
Вопрос: Какая область полей гистограммы отвечает за разбиение данных на столбцы по категориям?
\* Ответ: Область «Ось» (Axis).
Конструктор настройки визуального элемента:
1. Клик по иконке «Гистограмма с группировкой»
2. Перетаскивание поля Sales[Region] в область «Ось»
3. Перетаскивание меры [Общая выручка] в область «Значения»
4. Настройка форматирования и подписей данных
Практика:
Вопрос: Вам необходимо построить график продаж по месяцам с разделением по категориям товаров. Куда поместить категории товаров?
\* Ответ: В область «Легенда» (Legend).
