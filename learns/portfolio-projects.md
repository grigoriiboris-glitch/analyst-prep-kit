Проект 1. Анализ оттока клиентов и программы лояльности в E-commerce
1. Бизнес-кейс и проблематика
Интернет-магазин сталкивается со снижением повторных продаж. Отдел маркетинга запустил скидочные купоны для удержания покупателей, однако общая выручка продолжает снижаться. Необходимо оценить Churn Rate (коэффициент оттока), узнать влияние применения промокодов на пожизненную ценность клиента (LTV) и выделить сегменты клиентов без активных заказов.
Основные вопросы бизнеса:
\* Какова доля клиентов, прекративших совершать покупки в течение последних 90 дней?
\* Увеличивает ли использование купонов средний чек и повторную активность, или лишь снижает маржинальность?
\* Какие клиенты требуют срочных коммуницирующих воздействий (триггерных рассылок)?
2. Определение зернистости и структуры данных
Перед написанием запросов определяется зернистость (Grain) используемых таблиц:
\* Таблица customers: одна строка = один зарегистрированный клиент.
\* Таблица orders: одна строка = один заказ.
\* Поле coupon в orders: содержит код купона либо значение NULL.
3. Процесс выгрузки и трансформации данных (PostgreSQL)
Сборка витрины аналитики оттока с использованием агрегации, соединений INNER JOIN, операторов EXISTS и оконных функций.l
WITH customer\_orders AS (
SELECT
c.id AS customer\_id,
c.full\_name,
c.city,
COUNT(o.id) AS total\_orders,
SUM(CASE WHEN o.coupon IS NOT NULL THEN 1 ELSE 0 END) AS orders\_with\_coupon,
MAX(o.order\_ts) AS last\_order\_date
FROM customers AS c
INNER JOIN orders AS o ON c.id = o.customer\_id
WHERE c.active IS TRUE
GROUP BY c.id, c.full\_name, c.city
)
SELECT
customer\_id,
full\_name,
city,
total\_orders,
orders\_with\_coupon,
last\_order\_date,
EXTRACT(MONTH FROM last\_order\_date) AS last\_order\_month,
CASE
WHEN last\_order\_date < NOW() - INTERVAL '90 days' THEN 'Churned'
ELSE 'Active'
END AS churn\_status
FROM customer\_orders
ORDER BY total\_orders DESC;
Для поиска клиентов, у которых нет ни одного заказа за всё время (для исключения из анализа LTV и отправки приветственных офферов), применяется проверка `NOT EXISTS`:
```sql
SELECT
c.id,
c.full\_name,
c.city
FROM customers AS c
WHERE NOT EXISTS (
SELECT 1
FROM orders AS o
WHERE o.customer\_id = c.id
)
ORDER BY c.id;
4. Визуализация и бизнес-рекомендации
На основе полученных данных строится гистограмма распределения повторных заказов.
\* Длина столбцов отражает объем сегмента.
\* Цвет кодирует статус оттока (Active / Churned).
\* Результат анализа показывает: применение купонов повышает частоту заказов на 18%, но без ограничений по минимальному чеку снижает итоговую маржу. Рекомендуется ввести минимальный порог применения купона.
Проект 2. Анализ продаж и маржинальности розничной сети
1. Бизнес-кейс и проблематика
Крупная розничная сеть фиксирует рост валовой выручки при одновременном падении чистой прибыли. Руководству требуется инструмент регулярного мониторинга продаж в разрезе регионов, категорий товаров и филиалов.
Главная цель: идентифицировать «убыточные» категории товаров и регионы с неоптимальной логистикой, искажающие общий показатель доходности.
2. Очистка данных и обеспечение качества (Data Quality)
При импорте выгрузок из CSV-файлов возникает проблема несоответствия типов данных:
\* Числовые значения выручки импортируются как текстовые строки ('150), что приводит к ошибкам подсчета, когда функция =SUM() возвращает 0.
\* Выравнивание текста выполняется по левому краю, чисел — по правому.
Процесс подготовки данных в Excel:
1. Преобразование текстовых чисел в валидный численный тип через формулу =VALUE(A2).
2. Проверка корректности типов дат для расчета интервалов времени.
3. Исключение смешивания зернистости (запрет на нахождение ежедневных транзакций и ежемесячных итогов в одном столбце).
3. Моделирование и расчет показателей
Для расчета показателей без создания громоздких вспомогательных столбцов применяются логические формулы и функции условного агрегирования:
\* Категоризация заказов по объему выручки:
=IF(B2>1000, "High", "Low")
\* Расчет маржинальности с фильтрацией пустых значений:
=IF(C2="", "Missing", C2)
\* Использование абсолютных ссылок $B$1 для фиксации единой налоговой ставки или коэффициента затрат при протягивании формулы по тысячам строк.
4. Дизайн дашборда и визуальное кодирование
Для презентации результатов руководству формируется каскадная диаграмма (Waterfall chart), отражающая мост перехода от валовой выручки к операционной прибыли:
\* Начальный якорный столбец — Валовая выручка.
\* Плавающие столбцы — Себестоимость (-), Логистика (-), Маркетинг (-), Скидки (-).
\* Финальный якорный столбец — Чистая прибыль.
Использование Waterfall-диаграммы позволяет наглядно показать ключевой фактор падения маржи — непредвиденный рост транспортных расходов в Северном регионе.
Проект 3. Продуктовая аналитика воронки конверсии SaaS-платформы
1. Бизнес-кейс и ключевые гипотезы
Продуктовая команда SaaS-сервиса отмечает снижение конверсии из регистрации в оформление платной подписки. Необходимо проанализировать пользовательский путь (User Journey) от первого визита до проведения платежа, выявить этап с наибольшим отвалом и оценить влияние типа устройства.
Гипотезы:
\* Основной отвал происходит на шаге ввода платежных данных из-за отсутствия локальных способов оплаты.
\* Конверсия пользователей мобильных устройств существенно ниже, чем у пользователей ПК.
2. Подготовка и агрегация данных
Для анализа воронки используется лог событий (Events).
Зерно данных: одна строка = одно событие, совершенное пользователем в определенный момент времени (timestamptz).
Показатели расчета воронки:
\* Step 1: Visit (Сессия)
\* Step 2: Product View (Просмотр продукта)
\* Step 3: Add to Cart (Добавление в корзину)
\* Step 4: Checkout Start (Начало оформления)
\* Step 5: Payment Success (Успешная оплата)
3. Построение визуализации воронки в Tableau
Настройка рабочих областей Tableau выполняется в соответствии с циклом аналитика: Вопрос → Поле → Полка → Диаграмма → Инсайт.
1. Разделение полей на панели Data Pane:
\* Dimensions (Синие таблетки): Device Type, Region, Event Name — разбивают представление на категории.
\* Measures (Зеленые таблетки): User ID (в виде COUNTD), Amount — агрегируются в суммативы и средние значения.
2. Формирование воронки (Funnel Chart):
\* Перетаскивание Event Name на полку Rows.
\* Перетаскивание COUNTD(User ID) на полку Columns и карточку Marks (Size).
\* Добавление быстрого табличного вычисления (Percent of Total) для отображения доли прохождения каждого шага.
3. Сравнение конверсий по устройствам:
\* Перетаскивание Device Type на полку Columns или карточку Color.
\* Применение правила: длина полосы кодирует абсолютное количество пользователей, цвет — тип устройства.
4. Результаты анализа и управленческие решения
Анализ показал, что конверсия из Checkout Start в Payment Success на мобильных устройствах составляет всего 12% против 48% на Desktop. Причина — неадаптированная форма ввода карты на смартфонах.
Рекомендованное действие: переработка мобильного интерфейса оплаты и интеграция быстрой оплаты через мобильные платежные сервисы.

Чек-лист проверки готовности проекта к публикации
При оформлении проектов в портфолио (на GitHub или в виде интерактивных дашбордов) убедитесь в выполнении следующих требований:
\* Постановка бизнес-задачи: В начале описания указана конкретная проблема компании, а не просто перечень функций.
\* Качество и структура данных: Подтверждена проверка типов данных (отсутствие чисел в виде текста, корректный формат дат).
\* Четкая зернистость: Явно сформулировано правило «одна строка = одно наблюдение».
\* Корректность SQL/Формул: Запросы оптимизированы, отсутствуют лишние соединения типа CROSS JOIN, обработаны NULL-значения.
\* Визуальная грамотность: Оси гистограмм начинаются с нуля, выбран правильный визуальный канал (длина/положение вместо угла/площади).
\* Бизнес-выводы (Actionable Insights): Проект завершается конкретными рекомендациями для принятия управленческих решений.
