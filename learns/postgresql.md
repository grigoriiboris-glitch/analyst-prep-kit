## Урок 1. VERSION(): проверяем, что запущен PostgreSQL

**Раздел:** 0 · Старт

**Цель урока:**
  Увидеть версию PostgreSQL, в которой выполняется учебный запрос.

**Объяснение:**
  Функция VERSION() возвращает сведения о сервере PostgreSQL и его версии. Функцию можно вызвать прямо в списке SELECT, даже если таблица не нужна. В этом уроке тренируем только вызов VERSION().

**На что обратить внимание:**
  Не путай SQL и PostgreSQL: SQL — язык запросов, а PostgreSQL — СУБД. Функция VERSION() относится к PostgreSQL и не обязана существовать в других СУБД.

**Пример SQL:**
  
```sql
SELECT VERSION() AS postgres_version;
```

**starter Sql:**
  
```sql
SELECT 1 AS postgres_version;
```

**Задание:**
  Замени число 1 в заготовке на вызов функции, чтобы получить сведения о версии PostgreSQL.

**Критерии проверки:**
  **columns:**
    - postgres_version

  **column Order:**
    true

  **exact Rows:**
    1

  **sql Includes:**
    - version()

**Визуальный разбор:**
  - Запрос вызывает VERSION()
  - PostgreSQL возвращает строку
  - Результат имеет имя postgres_version

**Проверка понимания:**
  **Вопрос:** Что возвращает VERSION() в PostgreSQL?
  - Список таблиц базы
  - Сведения о версии сервера PostgreSQL — **правильный ответ**
  - Количество строк во всех таблицах
  **Разбор:** VERSION() возвращает текстовую информацию о запущенном сервере и его версии.

**Подсказка:**
  Какую встроенную функцию PostgreSQL можно вызвать без FROM, чтобы узнать версию сервера?

**Ожидаемый результат:**
  Столбец: postgres_version. Одна строка с текстом, в котором указаны PostgreSQL и номер версии. Точное значение зависит от версии движка учебной среды.

**Решение SQL:**
  
```sql
SELECT VERSION() AS postgres_version;
```

**Разбор решения:**
  VERSION() вызывается без аргументов и возвращает строку с информацией о сервере. AS postgres_version задаёт понятное имя столбца результата.

**Блоки для сборки:**
  - SELECT VERSION() AS postgres_version;
  - SELECT CURRENT_DATABASE() AS postgres_version;
  - SELECT VERSION() AS database_name;

## Урок 2. INFORMATION_SCHEMA.TABLES: список таблиц учебной схемы

**Раздел:** 0 · Старт

**Цель урока:**
  Посмотреть, какие таблицы доступны в схеме public.

**Объяснение:**
  INFORMATION_SCHEMA.TABLES — системное представление PostgreSQL, в котором описаны таблицы и представления базы. Поле table_schema показывает схему, а table_name — имя объекта. Чтобы увидеть таблицы учебной схемы, выбери строки со значением public.

**На что обратить внимание:**
  Не ищи таблицу только по имени, если в базе есть несколько схем. Одноимённые таблицы из разных схем могут быть разными объектами.

**Пример SQL:**
  
```sql
SELECT table_schema,
       table_name
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY table_name;
```

**starter Sql:**
  
```sql
SELECT table_schema,
       table_name
FROM information_schema.tables
WHERE table_schema = 'information_schema'
ORDER BY table_name;
```

**Задание:**
  Получи список объектов схемы public и найди в нём таблицу orders.

**Критерии проверки:**
  **columns:**
    - table_schema
    - table_name

  **column Order:**
    true

  **exact Rows:**
    7

  **contains:**
    **column:**
      table_name

    **value:**
      orders

  **sql Includes:**
    - where table_schema = 'public'

**Визуальный разбор:**
  - INFORMATION_SCHEMA.TABLES содержит описание объектов
  - WHERE оставляет схему public
  - В результате видны 7 учебных таблиц

**Проверка понимания:**
  **Вопрос:** Какое поле показывает схему, в которой находится таблица?
  - table_name
  - table_schema — **правильный ответ**
  - table_type
  **Разбор:** table_schema хранит имя схемы, а table_name — имя объекта внутри неё.

**Подсказка:**
  В каком значении table_schema находятся таблицы учебной схемы, а не служебные представления PostgreSQL?

**Ожидаемый результат:**
  Столбцы в таком порядке: table_schema, table_name. В учебной схеме public ожидается 7 таблиц: customers, order_items, orders, page_events, payments, products и support_tickets.

**Решение SQL:**
  
```sql
SELECT table_schema,
       table_name
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY table_name;
```

**Разбор решения:**
  Представление information_schema.tables показывает объекты базы. Условие оставляет только схему public, а ORDER BY располагает имена таблиц по алфавиту.

**Блоки для сборки:**
  - SELECT table_schema,
  - table_name
  - FROM information_schema.tables
  - WHERE table_schema = 'public'
  - ORDER BY table_name;
  - WHERE table_schema = 'information_schema'
  - ORDER BY table_name DESC;

## Урок 3. AS: задаём псевдоним столбцу результата

**Раздел:** 1 · Запросы и фильтрация

**Цель урока:**
  Переименовать столбец только в результате запроса.

**Объяснение:**
  Псевдоним задаёт столбцу результата новое, более понятное имя. В PostgreSQL для этого используют AS: выражение AS alias. Псевдоним не меняет название поля в исходной таблице.

**На что обратить внимание:**
  Не заключай псевдоним в одинарные кавычки: 'customer_name' — строковое значение, а не имя столбца. Для обычных псевдонимов кавычки вообще не нужны.

**Пример SQL:**
  
```sql
SELECT full_name AS customer_name,
       city
FROM customers
ORDER BY id;
```

**starter Sql:**
  
```sql
SELECT full_name,
       city
FROM customers
ORDER BY id;
```

**Задание:**
  Покажи имя клиента под названием customer_name, оставив рядом его город.

**Критерии проверки:**
  **columns:**
    - customer_name
    - city

  **column Order:**
    true

  **exact Rows:**
    13

  **first Row:**
    **customer_name:**
      Анна Кузнецова

    **city:**
      Москва

  **sql Includes:**
    - as customer_name

**Визуальный разбор:**
  - full_name хранится в customers
  - AS задаёт новое имя в выдаче
  - В результате отображается customer_name

**Проверка понимания:**
  **Вопрос:** Что делает AS customer_name?
  - Физически переименовывает поле customers
  - Задаёт имя столбца только в результате запроса — **правильный ответ**
  - Создаёт новую таблицу
  **Разбор:** Псевдоним существует только в результате запроса и не меняет структуру исходной таблицы.

**Подсказка:**
  Какое ключевое слово нужно поставить после full_name, чтобы назвать этот столбец customer_name только в результате?

**Ожидаемый результат:**
  Столбцы в таком порядке: customer_name, city. Например: Анна Кузнецова | Москва; Борис Смирнов | Казань; Вера Орлова | Москва.

**Решение SQL:**
  
```sql
SELECT full_name AS customer_name,
       city
FROM customers
ORDER BY id;
```

**Разбор решения:**
  SELECT выбирает имя и город из customers. AS customer_name меняет только подпись первого столбца в выдаче; исходное поле по-прежнему называется full_name.

**Блоки для сборки:**
  - SELECT full_name AS customer_name,
  - city
  - FROM customers
  - ORDER BY id;
  - full_name AS full_name,
  - ORDER BY full_name;

## Урок 4. WHERE: отбираем активных клиентов

**Раздел:** 1 · Запросы и фильтрация

**Цель урока:**
  Оставить в результате только строки, которые подходят под условие.

**Объяснение:**
  WHERE проверяет каждую строку до того, как она попадёт в результат. После WHERE указывают условие, которое должно быть истинным. Для логического поля active значение TRUE означает, что клиент активен.

**На что обратить внимание:**
  Не записывай логическое условие как active = 'true': в одинарных кавычках находится текст. Для boolean используй TRUE или FALSE без кавычек.

**Пример SQL:**
  
```sql
SELECT id,
       full_name,
       city
FROM customers
WHERE active IS TRUE
ORDER BY id;
```

**starter Sql:**
  
```sql
SELECT id,
       full_name,
       city
FROM customers
ORDER BY id;
```

**Задание:**
  Выведи только активных клиентов, сохранив идентификатор, имя и город.

**Критерии проверки:**
  **columns:**
    - id
    - full_name
    - city

  **column Order:**
    true

  **exact Rows:**
    12

  **first Row:**
    **full_name:**
      Анна Кузнецова

  **sql Includes:**
    - where active is true

**Визуальный разбор:**
  - Таблица содержит всех клиентов
  - WHERE проверяет active
  - Остаются только активные строки

**Проверка понимания:**
  **Вопрос:** На каком этапе запроса WHERE отбирает строки?
  - До группировки и вычисления агрегатов — **правильный ответ**
  - После ORDER BY
  - Только после LIMIT
  **Разбор:** WHERE сначала отбирает исходные строки, а затем оставшиеся данные обрабатываются следующими частями запроса.

**Подсказка:**
  Какое поле показывает активность клиента и какое значение должно быть у него, чтобы строка осталась в результате?

**Ожидаемый результат:**
  Столбцы: id, full_name, city. Ожидается 12 активных клиентов. Первые примеры: 1 | Анна Кузнецова | Москва; 2 | Борис Смирнов | Казань; 4 | Глеб Иванов | Санкт-Петербург.

**Решение SQL:**
  
```sql
SELECT id,
       full_name,
       city
FROM customers
WHERE active IS TRUE
ORDER BY id;
```

**Разбор решения:**
  WHERE отбрасывает клиентов, у которых active не равно TRUE. В учебных данных неактивен клиент с id = 3, поэтому в результате остаются 12 строк.

**Блоки для сборки:**
  - SELECT id,
  - full_name,
  - city
  - FROM customers
  - WHERE active IS TRUE
  - ORDER BY id;
  - WHERE active IS FALSE
  - ORDER BY full_name;

## Урок 5. IS NULL: находим заказы без купона

**Раздел:** 1 · Запросы и фильтрация

**Цель урока:**
  Найти строки, в которых значение отсутствует.

**Объяснение:**
  NULL означает, что значение неизвестно или не задано. Для поиска таких строк в PostgreSQL используют IS NULL, а для строк с заполненным значением — IS NOT NULL. NULL нельзя проверять обычным знаком равенства.

**На что обратить внимание:**
  Условие coupon = NULL не найдёт пропуски: сравнение с NULL даёт неизвестный результат. Используй именно IS NULL; пустая строка '' — отдельное значение.

**Пример SQL:**
  
```sql
SELECT id,
       coupon
FROM orders
WHERE coupon IS NULL
ORDER BY id;
```

**starter Sql:**
  
```sql
SELECT id,
       coupon
FROM orders;
```

**Задание:**
  Найди все заказы, в которых купон не указан. Покажи номер заказа и значение coupon.

**Критерии проверки:**
  **columns:**
    - id
    - coupon

  **column Order:**
    true

  **exact Rows:**
    10

  **sql Includes:**
    - coupon is null

**Визуальный разбор:**
  - В поле coupon есть NULL
  - IS NULL проверяет отсутствие значения
  - В выдаче остаются 9 заказов без купона

**Проверка понимания:**
  **Вопрос:** Как правильно выбрать строки, где coupon отсутствует?
  - coupon = NULL
  - coupon IS NULL — **правильный ответ**
  - coupon = ''
  **Разбор:** IS NULL проверяет отсутствие значения. Пустая строка и NULL не означают одно и то же.

**Подсказка:**
  Какое специальное условие проверяет отсутствие значения, а не сравнивает coupon с пустым текстом?

**Ожидаемый результат:**
  Столбцы: id, coupon. Ожидается 10 строк; во всех coupon отображается как NULL. Первые номера заказов: 102, 104 и 106.

**Решение SQL:**
  
```sql
SELECT id,
       coupon
FROM orders
WHERE coupon IS NULL
ORDER BY id;
```

**Разбор решения:**
  IS NULL оставляет только заказы без значения coupon. ORDER BY id упорядочивает найденные заказы по номеру.

**Блоки для сборки:**
  - SELECT id,
  - coupon
  - FROM orders
  - WHERE coupon IS NULL
  - ORDER BY id;
  - WHERE coupon = NULL
  - ORDER BY id DESC;

## Урок 6. ILIKE: поиск текста без учёта регистра

**Раздел:** 1 · Запросы и фильтрация

**Цель урока:**
  Найти адреса электронной почты по текстовому шаблону.

**Объяснение:**
  ILIKE сравнивает текст без учёта регистра и является расширением PostgreSQL. Знак % в шаблоне означает любую последовательность символов, в том числе пустую. Например, шаблон с окончанием почтового домена помогает найти все адреса этого домена.

**На что обратить внимание:**
  Не ставь шаблон в двойные кавычки: двойные кавычки обозначают имена объектов. Строковый шаблон всегда заключай в одинарные кавычки.

**Пример SQL:**
  
```sql
SELECT id,
       full_name,
       email
FROM customers
WHERE email ILIKE '%@example.ru'
ORDER BY id;
```

**starter Sql:**
  
```sql
SELECT id,
       full_name,
       email
FROM customers;
```

**Задание:**
  Найди клиентов с адресами почты, которые заканчиваются на @example.ru, независимо от регистра букв.

**Критерии проверки:**
  **columns:**
    - id
    - full_name
    - email

  **column Order:**
    true

  **exact Rows:**
    11

  **first Row:**
    **email:**
      anna@example.ru

  **sql Includes:**
    - ilike '%@example.ru'

**Визуальный разбор:**
  - email содержит адрес
  - ILIKE сравнивает без учёта регистра
  - % заменяет произвольную часть адреса

**Проверка понимания:**
  **Вопрос:** Что означает знак % в шаблоне ILIKE '%@example.ru'?
  - Ровно один символ
  - Любую последовательность символов, включая пустую — **правильный ответ**
  - Только цифры
  **Разбор:** Процент заменяет любое количество символов. Поэтому шаблон находит адреса с разной частью до домена.

**Подсказка:**
  Какой оператор PostgreSQL подходит для поиска по шаблону, если заглавные и строчные буквы нужно считать одинаковыми?

**Ожидаемый результат:**
  Столбцы: id, full_name, email. Ожидается 11 клиентов с доменом example.ru. Примеры: 1 | anna@example.ru; 2 | boris@example.ru; 3 | vera@example.ru.

**Решение SQL:**
  
```sql
SELECT id,
       full_name,
       email
FROM customers
WHERE email ILIKE '%@example.ru'
ORDER BY id;
```

**Разбор решения:**
  ILIKE проверяет, соответствует ли email шаблону без учёта регистра. Символ % перед @example.ru допускает любую часть адреса до домена.

**Блоки для сборки:**
  - SELECT id,
  - full_name,
  - email
  - FROM customers
  - WHERE email ILIKE '%@example.ru'
  - ORDER BY id;
  - WHERE email LIKE '%@example.ru'
  - WHERE email ILIKE 'example.ru';

## Урок 7. ORDER BY: сортируем строки результата

**Раздел:** 1 · Запросы и фильтрация

**Цель урока:**
  Получить заказы в нужной последовательности.

**Объяснение:**
  ORDER BY задаёт порядок строк в результате запроса. По умолчанию используется возрастание ASC, а DESC задаёт убывание. Для сортировки по дате сначала укажи поле order_ts, а затем DESC, чтобы новые заказы оказались сверху.

**На что обратить внимание:**
  Без ORDER BY база не обязана возвращать строки в порядке вставки или по первичному ключу. Не полагайся на случайный порядок результата.

**Пример SQL:**
  
```sql
SELECT id,
       customer_id,
       order_ts,
       status
FROM orders
ORDER BY order_ts DESC, id DESC;
```

**starter Sql:**
  
```sql
SELECT id,
       customer_id,
       order_ts,
       status
FROM orders;
```

**Задание:**
  Выведи заказы от самого нового к самому старому. При одинаковой дате используй id как дополнительный критерий сортировки.

**Критерии проверки:**
  **columns:**
    - id
    - customer_id
    - order_ts
    - status

  **column Order:**
    true

  **exact Rows:**
    20

  **sql Includes:**
    - order by order_ts desc

**Визуальный разбор:**
  - ORDER BY получает поле сортировки
  - DESC ставит поздние даты выше
  - id разрешает равенство дат

**Проверка понимания:**
  **Вопрос:** Что делает DESC в ORDER BY?
  - Сортирует значения по убыванию — **правильный ответ**
  - Удаляет повторяющиеся строки
  - Ограничивает количество строк
  **Разбор:** DESC означает обратный порядок: от большего к меньшему или от более поздней даты к ранней.

**Подсказка:**
  Какой порядок нужен для самых свежих дат в начале списка: ASC или DESC? Что поможет упорядочить строки с одинаковой датой?

**Ожидаемый результат:**
  Столбцы: id, customer_id, order_ts, status. Всего 20 строк. Первая строка — заказ 120, затем заказ 119 и заказ 118.

**Решение SQL:**
  
```sql
SELECT id,
       customer_id,
       order_ts,
       status
FROM orders
ORDER BY order_ts DESC, id DESC;
```

**Разбор решения:**
  ORDER BY order_ts DESC ставит самые поздние даты первыми. Дополнительная сортировка по id DESC делает порядок однозначным, когда у нескольких заказов совпадает время.

**Блоки для сборки:**
  - SELECT id,
  - customer_id,
  - order_ts,
  - status
  - FROM orders
  - ORDER BY order_ts DESC, id DESC;
  - ORDER BY order_ts ASC, id ASC;
  - LIMIT 5;

## Урок 8. Приведение типа через ::INTEGER

**Раздел:** 2 · Типы и время

**Цель урока:**
  Преобразовать текстовое значение в целое число.

**Объяснение:**
  В PostgreSQL тип значения можно указать после двух двоеточий. Запись value::INTEGER пытается преобразовать value в целое число. Если текст нельзя представить целым числом, PostgreSQL вернёт ошибку.

**На что обратить внимание:**
  Не заключай тип INTEGER в одинарные кавычки и не используй десятичную запятую в числовом литерале. Строку для преобразования записывай в одинарных кавычках, а тип — без кавычек.

**Пример SQL:**
  
```sql
SELECT '42'::INTEGER AS parsed_id,
       PG_TYPEOF('42'::INTEGER) AS result_type;
```

**starter Sql:**
  
```sql
SELECT '42'::TEXT AS parsed_id,
       PG_TYPEOF('42'::TEXT) AS result_type;
```

**Задание:**
  Преобразуй текст '42' в целое число и проверь тип полученного значения.

**Критерии проверки:**
  **columns:**
    - parsed_id
    - result_type

## Урок 11. GROUP BY: считаем заказы по статусам

**Цель урока:**

**Объяснение:**

WHERE отбирает отдельные строки до группировки, а HAVING фильтрует уже собранные группы. В этой практике тренируем только GROUP BY; HAVING используй, когда нужно оставить группы по условию на агрегат.

**На что обратить внимание:**
  Не добавляй в SELECT поля, которые не сгруппированы и не обёрнуты в агрегатную функцию: PostgreSQL сообщит об ошибке. Сначала реши, на каком уровне должна быть одна строка результата.

```sql
SELECT status,
```

  - Во всех будущих подключениях к базе
  - Как имя новой постоянной таблицы

## Урок 16. WITH RECURSIVE: строим последовательность шаг за шагом

**Раздел:** 4 · Связи и сложные запросы

**Цель урока:**
  Понять начальную и повторяющуюся части рекурсивного запроса.

**Объяснение:**
  WITH RECURSIVE позволяет запросу ссылаться на собственный результат. Сначала выполняется начальная часть, задающая стартовые строки; затем рекурсивная часть добавляет новые строки. Рекурсия заканчивается, когда условие следующего шага больше не выполняется.

**На что обратить внимание:**
  Не забывай условие остановки. Если рекурсивная часть продолжает создавать новые строки бесконечно, запрос может долго выполняться или завершиться по ограничению среды.

**Пример SQL:**
  
```sql
WITH RECURSIVE levels(level) AS (
    SELECT 1
    UNION ALL
    SELECT level + 1
    FROM levels
    WHERE level < 5
)
SELECT level
FROM levels
ORDER BY level;
```

**starter Sql:**
  
```sql
WITH RECURSIVE levels(level) AS (
    SELECT 1
)
SELECT level
FROM levels;
```

**Задание:**

    5

    **level:**
      1

  **sql Includes:**
    - union all
    - from levels
    - where level < 5

**Визуальный разбор:**
  - Начальная часть создаёт 1
  - Рекурсивная часть прибавляет 1
  - Условие level < 5 останавливает цикл

**Проверка понимания:**
  **Вопрос:** Какие части есть у простого рекурсивного CTE?
  - Начальная выборка и рекурсивная часть — **правильный ответ**
  - Только ORDER BY и LIMIT
  - CREATE TABLE и CREATE INDEX

## Урок 17. ROW_NUMBER(): нумеруем строки внутри группы

**Раздел:** 4 · Связи и сложные запросы

**Цель урока:**
  Пронумеровать заказы каждого клиента по дате.

**Объяснение:**
  ROW_NUMBER() — оконная функция PostgreSQL, которая присваивает каждой строке номер внутри окна. PARTITION BY начинает нумерацию заново для каждого клиента, а ORDER BY задаёт порядок строк внутри его группы. В отличие от GROUP BY, оконная функция сохраняет отдельную строку для каждого заказа.

**На что обратить внимание:**

**Пример SQL:**
  
```sql
SELECT customer_id,
       id AS order_id,
       order_ts,
       ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY order_ts DESC, id DESC
       ) AS order_rank
FROM orders
ORDER BY customer_id, order_ts DESC, id DESC;
```

**starter Sql:**
  
```sql
SELECT customer_id,
       id AS order_id,
       order_ts
FROM orders
ORDER BY customer_id, order_ts DESC, id DESC;
```

**Задание:**

**Критерии проверки:**
  **columns:**
    - customer_id
    - order_id
    - order_ts
    - order_rank

  **column Order:**
    true

  **exact Rows:**
    20

  **first Row:**
    **customer_id:**
      1

    **order_id:**
      102

    **order_rank:**
      1

  **sql Includes:**
    - row_number() over
    - partition by customer_id

**Визуальный разбор:**
  - Заказы разделяются по customer_id
  - ROW_NUMBER присваивает номер в группе
  - Самый новый заказ получает 1

**Проверка понимания:**
  **Вопрос:** Зачем в окне ROW_NUMBER() используется PARTITION BY customer_id?
  - Чтобы начинать нумерацию отдельно для каждого клиента — **правильный ответ**
  - Чтобы удалить клиентов без заказов
  - Чтобы сгруппировать результат в одну строку
  **Разбор:** PARTITION BY разделяет строки на независимые группы, в каждой из которых нумерация начинается с 1.

**Подсказка:**
  Какую оконную функцию нужно добавить и по какому полю разделить строки, чтобы нумерация начиналась заново у каждого клиента?

```sql
ORDER BY customer_id, order_ts DESC, id DESC;
```

**Разбор решения:**

**Блоки для сборки:**

  - PARTITION BY customer_id
  - ORDER BY order_ts DESC, id DESC
  - ) AS order_rank
  - FROM orders

```sql
SELECT city AS location,

FROM customers
UNION ALL
SELECT channel AS location,

FROM orders
ORDER BY source, location;
```

```sql
FROM customers;
```

  - Второй SELECT возвращает каналы

  - UNION ALL сохраняет повторяющиеся строки — **правильный ответ**
  - UNION ALL объединяет только числа
  - UNION ALL всегда сортирует результат

## Урок 21. ON CONFLICT DO UPDATE: обновляем строку при совпадении ключа

**Раздел:** 5 · Модель данных и изменения

**Цель урока:**
  Вставить запись или обновить существующую без создания дубликата.

**Объяснение:**
  В PostgreSQL конструкция INSERT ... ON CONFLICT задаёт действие при нарушении уникальности. DO UPDATE обновляет найденную конфликтующую строку, а EXCLUDED содержит значения, которые пытались вставить. Для этого урока ключом конфликта выступает products.id.

**На что обратить внимание:**
  ON CONFLICT сработает только при конфликте с подходящим уникальным ограничением или индексом. Укажи правильный ключ, иначе PostgreSQL не сможет определить, какой конфликт обрабатывать.

**Пример SQL:**
  
```sql
INSERT INTO products (id, name, category, price, tags)
VALUES (99, 'Учебный товар', 'Аксессуары', 100, ARRAY['demo']::TEXT[])
ON CONFLICT (id) DO UPDATE
SET price = EXCLUDED.price
RETURNING id, name, price;
```

**starter Sql:**
  
```sql
INSERT INTO products (id, name, category, price, tags)
VALUES (99, 'Учебный товар', 'Аксессуары', 100, ARRAY['demo']::TEXT[])
ON CONFLICT (id) DO NOTHING
RETURNING id, name, price;
```

**Задание:**
  Добавь учебный товар с id = 99. При повторном запуске запроса должна обновляться цена существующей записи, а не появляться новая строка.

**Критерии проверки:**
  **columns:**
    - id
    - name
    - price

  **column Order:**
    true

  **exact Rows:**
    1

  **first Row:**
    **price:**
      100

  **sql Includes:**
    - on conflict (id) do update
    - excluded.price

**Визуальный разбор:**
  - INSERT предлагает товар с id 99
  - ON CONFLICT проверяет уникальный ключ
  - DO UPDATE обновляет цену через EXCLUDED

**Проверка понимания:**
  **Вопрос:** Что означает EXCLUDED.price внутри DO UPDATE?
  - Цена из уже существующей строки
  - Цена, которую текущий INSERT пытался записать — **правильный ответ**
  - Средняя цена всех товаров
  **Разбор:** EXCLUDED обращается к значениям строки, предложенной командой INSERT.

**Подсказка:**

## Урок 22. ROLLBACK: отменяем изменения внутри транзакции

**Раздел:** 5 · Модель данных и изменения

**Цель урока:**
  Проверить изменение и отменить его до подтверждения транзакции.

**Объяснение:**
  Транзакция объединяет несколько SQL-команд в одну операцию. BEGIN начинает транзакцию, ROLLBACK отменяет её незавершённые изменения, а COMMIT подтверждает их. После ROLLBACK данные должны вернуться к состоянию до BEGIN.

**На что обратить внимание:**
  ROLLBACK отменяет изменения только до COMMIT. Если сначала выполнить COMMIT, обычный ROLLBACK уже не восстановит исходные данные.

**Пример SQL:**
  
```sql
BEGIN;
UPDATE orders
SET status = 'cancelled'
WHERE id = 101
RETURNING id, status AS status_in_transaction;
ROLLBACK;
SELECT id,
       status AS status_after_rollback
FROM orders
WHERE id = 101;
```

**starter Sql:**
  
```sql
BEGIN;
UPDATE orders
SET status = status
WHERE id = 101
RETURNING id, status AS status_in_transaction;
COMMIT;
SELECT id,
       status AS status_after_rollback
FROM orders
WHERE id = 101;
```

**Задание:**
  Временно измени статус заказа 101 на cancelled, затем отмени изменение и последним SELECT проверь исходный статус.

**Критерии проверки:**
  **columns:**
    - id
    - status_after_rollback

  **column Order:**
    true

  **exact Rows:**
    1

  **first Row:**
    **status_after_rollback:**
      paid

  **sql Includes:**
    - rollback
    - status_after_rollback

**Визуальный разбор:**
  - BEGIN начинает транзакцию
  - UPDATE временно меняет статус
  - ROLLBACK отменяет изменение, SELECT показывает paid

**Проверка понимания:**
  **Вопрос:** Что произойдёт после ROLLBACK до COMMIT?
  - Изменения текущей транзакции будут отменены — **правильный ответ**
  - Изменения станут постоянными
  - Создастся копия таблицы
  **Разбор:** ROLLBACK отменяет все незакоммиченные изменения текущей транзакции.

**Подсказка:**
  Какую команду нужно поставить вместо COMMIT, чтобы отменить изменение? Как проверить значение после завершения транзакции?

**Ожидаемый результат:**
  Последний результат: столбцы id, status_after_rollback. Одна строка: 101 | paid. Во время транзакции UPDATE вернёт cancelled, но после отката в таблице останется paid.

**Решение SQL:**
  
```sql
BEGIN;
UPDATE orders
SET status = 'cancelled'
WHERE id = 101
RETURNING id, status AS status_in_transaction;
ROLLBACK;
SELECT id,
       status AS status_after_rollback
FROM orders
WHERE id = 101;
```

**Разбор решения:**
  BEGIN открывает транзакцию, UPDATE временно меняет статус заказа и RETURNING показывает это промежуточное значение. ROLLBACK отменяет изменение; завершающий SELECT подтверждает, что в таблице по-прежнему хранится paid.

**Блоки для сборки:**
  - BEGIN;
  - UPDATE orders
  - SET status = 'cancelled'
  - WHERE id = 101
  - RETURNING id, status AS status_in_transaction;
  - ROLLBACK;
  - SELECT id,
  - status AS status_after_rollback
  - FROM orders
  - WHERE id = 101;

  - SELECT id, status FROM orders WHERE id = 102;

## Урок 29. CURRENT_USER: узнаём роль текущей сессии

**Раздел:** 7 · Рабочий процесс и безопасность

**Цель урока:**
  Посмотреть, под какой ролью выполняется запрос.

**Объяснение:**
  CURRENT_USER возвращает имя роли, от имени которой выполняется текущий запрос. В PostgreSQL роль определяет доступные действия и права на объекты. Команды GRANT и REVOKE применяют на реальном сервере, чтобы выдавать и отзывать права; учебная песочница показывает текущую роль, но не заменяет настройку доступа production-базы. На реальном сервере администратор выдаёт права через GRANT и отзывает их через REVOKE; здесь тренируем только чтение имени текущей роли, поскольку браузерная песочница не настраивает серверные учётные записи.

**На что обратить внимание:**
  Не публикуй учётные данные и не выдавай приложению роль superuser. В рабочей базе назначай только те права, которые действительно нужны пользователю или приложению.

## Урок 30. Итоговый проект: выручка магазина по месяцам и категориям

**Раздел:** 8 · Итоговый кейс

**Цель урока:**
  Собрать отчёт, который объединяет уже изученные приёмы SQL.

**Объяснение:**
  В итоговом проекте используются CTE, соединение таблиц, группировка, агрегаты и работа с датами. Заказ считается принятым, если его статус paid или fulfilled; выручка рассчитывается как quantity × unit_price по товарным позициям. Результат показывает отдельную строку для каждого месяца и категории товара.

**На что обратить внимание:**
  Не суммируй order_total после JOIN с несколькими товарными позициями без проверки уровня детализации: строки могут размножиться. В этом проекте сумма считается из order_items, а бизнес-правило явно ограничено статусами paid и fulfilled.

**Пример SQL:**
  
```sql
WITH accepted_orders AS (
    SELECT id,
           order_ts
    FROM orders
    WHERE status IN ('paid', 'fulfilled')
), revenue_by_order AS (
    SELECT oi.order_id,
           p.category,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM order_items AS oi
    INNER JOIN products AS p
            ON p.id = oi.product_id
    GROUP BY oi.order_id, p.category
)
SELECT DATE_TRUNC('month', ao.order_ts)::DATE AS month,
       r.category,
       COUNT(DISTINCT ao.id) AS orders_count,
       SUM(r.revenue) AS revenue
FROM accepted_orders AS ao
INNER JOIN revenue_by_order AS r
        ON r.order_id = ao.id
GROUP BY 1, r.category
ORDER BY month, revenue DESC;
```
